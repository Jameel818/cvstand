# CVStand Templates Guide: Website = Word = PDF

> **What this file is for.** It covers how CVStand templates are built, edited, replaced and checked so that the **Word (.docx)** and **PDF** downloads look exactly like the template shown on the website. It collects what we learned in fidelity runs 4–14, the Arabic Word review (2026-10-06) and the typography spec (`CVSTAND_FONT_CONTROLS.md`).
>
> **Who reads it:** you, a teammate, or Claude Code. If you are Claude Code, read the whole file first, start in **Plan Mode**, and wait for approval before changing code.
>
> **Status markers used below**
> - ✅ **Confirmed**: decided or tested in earlier runs.
> - 🔍 **Verify in repo**: the path or name is our best knowledge but has not been checked against the current code. Check it and correct this file (see §15).

## 1. The golden rule

**The website preview is the master design.** The PDF and the Word file are copies of it and must match it.

| Output | How it is made | How close it must be |
|---|---|---|
| Website preview | HTML + CSS in the browser | This is the reference |
| PDF | The same HTML rendered by Playwright/Chromium | Should be pixel-identical to the preview |
| Word (.docx) | Rebuilt separately with python-docx (per-template Word design) | Visually identical: same layout, colours, fonts, sizes and page count. It must stay editable. |

**Approved downloads are locked (§17).** A change may only touch templates the task names. Run the download-lock test before every commit. Never update the lock without the owner's approval.

Why Word needs the most care: the PDF comes from the **same HTML**, so it nearly matches by default. Word has **no HTML engine**, so every template is drawn a second time in Word's own language (tables, paragraphs, DrawingML shapes). Most of our fidelity bugs were on the Word side.

**Rendering pipeline**

```
CV data (flat JSON, "language": "en" | "ar")
        │
        ├──► HTML template + CSS ──► Website preview
        │                     └──► Playwright: load page → document.fonts.ready
        │                          → fonts.load() each face → fonts.check() → page.pdf()  ──► PDF
        │
        └──► Word design for this template (python-docx)
              → save → embed_fonts() post-process ──► .docx
```

### 3.1 Page size and units: TWO papers ✅

Every CV is on **A4 or US Letter** (since 2026-11-17, `feature/paper-size`). All the numbers below come from `app/paper.py`; never write them as literals in a template, an exporter or a Word design.

**The canvas is always 850px wide; only the height changes.** That is what lets one template serve both papers: every width-keyed and absolutely positioned layout is drawn against 850.

| | **US Letter** | **A4** |
|---|---|---|
| Canvas (preview) | **850 × 1100px** | **850 × 1202px** |
| Template root | `height:{{ page.h }}px` (1100) | `height:{{ page.h }}px` (1202) |
| `@page` of the document | `850px 1100px` | `850px 1202px` |
| Printed size of 1px (PDF and Word) | **0.72pt** | **0.70033pt** (595.28 / 850) |
| PDF sheet | 612 × 792pt: `format="Letter"`, `scale=0.96` (`PDF_SCALE`), `@page { size: 8.5in 11in }` | **594.96 × 841.92pt**: `format="A4"`, `scale=0.93327`, `@page { size: 210mm 297mm }`. Chromium cannot emit ISO's 595.28 × 841.89pt whatever `@page` says; this is the sheet Chrome's own "Save as PDF > A4" makes (0.32pt off, inside ISO 216). |
| Word section | 12240 × 15840 twips (612 × 792pt) | 11906 × 16838 twips (595.3 × 841.9pt) |

**Which paper a CV is on.**
- `paper` is an optional root field of the résumé. **Missing means Letter**: every CV saved before the feature keeps the page it was approved on, and every Letter golden stays valid.
- A **new** CV starts on A4, or on Letter when the browser language is en-US / en-CA. The user can switch, and Undo restores the previous paper.
- `normalize()` does not add `paper`; templates read `page` instead.

**PDF** (`app/exporters/pdf.py`, `page_css(paper)`). Use `page.pdf(format=paper.pdf_format, scale=…, margin 0, prefer_css_page_size=True)`, after adding the paper's `@page` size to the headless page only. Don't add a `scale` without that `@page` override: with `prefer_css_page_size` off, Chromium already shrinks the 850px `@page` to fit the paper, and a scale on top shrinks it twice (measured: 0.9216). `tests/e2e/test_pdf_letter_page.py` and `tests/e2e/test_pdf_a4_page.py` check the sheet AND the text size.

**Word** (Modern `word_designs/tN.py` + `common.py`, ATS `docx_ats.py`, letters `docx_letter.py`). Work in template px through the helpers in `app/exporters/docx_design.py`, which follow the bound paper:
- `pt(px)` and `tw(px)` convert template px to points and twips.
- `px_pt()` gives the points per px for the current paper.
- `page_h_px()`, `page_w_pt()`, `page_h_pt()` and `page_w_tw()` give the page size.

**Never** write `1100`, `612`, `792`, `12240` or `/ 0.72` in Word code: each one is a place where A4 silently comes out 50pt short. Full-height rails and sidebars are `page_h_px()` tall.

The PDF and Word therefore have the same page and the same sizes on each paper: an 11px body is 7.92pt on Letter and 7.70pt on A4, in both outputs.

---|---|---|
| Template (preview) | **850×1100px canvas** (US Letter proportions); `@page { size: 850px 1100px; margin: 0 }` in `app/rendering.py` | px, as inline `style="…"` attributes in the `.j2` |
| PDF | **US Letter, 612 × 792pt** (since 2026-11-10): `page.pdf(format="Letter", scale=0.96, margin 0, prefer_css_page_size=True)` after adding `@page { size: 8.5in 11in }` to the headless page only (`app/exporters/pdf.py`, `PDF_SCALE`). Before that it printed 637.92 × 824.88pt, about 4% larger than Letter. | **1px = 0.72pt** (0.75pt per CSS px × 0.96), the same as Word |
| Word, Modern | **US Letter, 612×792pt** (`PAGE_W = 12240` twips, `PAGE_H_PT = 792`) | **1px = 0.72pt** (`PX = 0.72` in `app/exporters/docx_design.py`; `pt(px)`, `tw(px)` = twips). The 24 `word_designs/tN.py` modules and `word_designs/common.py` work in template px through these helpers. |
| Word, ATS | US Letter, 612×792pt | **1px = 0.72pt** (`app/exporters/docx_ats.py` reads each inline style and converts it) |

The PDF and Word therefore have the same page and the same sizes: an 11px body is 7.92pt in both. Don't add a `scale` to `page.pdf()` without the `@page` override: with `prefer_css_page_size` off, Chromium already shrinks the 850px `@page` to fit the paper, and a scale on top shrinks it twice (measured: 0.9216). `tests/e2e/test_pdf_letter_page.py` checks both the page size and the text size.

## 4. Lifecycle: adding a NEW template (start to finish)

Follow these steps in order, and finish each one before starting the next.

> **Two papers, always.** Every NEW or REPLACED template is checked on **BOTH paper sizes, US Letter AND A4**: preview, PDF and Word, in EN and AR. A template that is one page on Letter can still overflow on A4 in Word (A4 is narrower in points). A rail that ends at 1100px leaves a 102px gap on A4.

### Step 1: Design brief
- Pick the group (Modern or ATS), a name in **EN and AR**, a colour palette, and fonts from the **font registry only**.
- Write down every visual element, because each one will need a Word equivalent: bands, sidebars, page tint, timeline, pills, photo frame, skill bars/dots, icons, dividers.
- ⚠️ Avoid effects Word cannot reproduce (see §8.10). If the design needs one, agree on the Word fallback **before** building.

### Step 2: HTML + CSS (the master)
- Use **CSS variables** for fonts and sizes (`--font-heading`, `--font-heading-weight`, `--font-heading-size`, `--font-body`, …).
- Write sizes in **px as inline `style="…"` attributes** on the **850px-wide canvas**. The root's height is **`height:{{ page.h }}px`** (1100 on Letter, 1202 on A4), **never a literal 1100**, and so is anything that runs the full page height (rails, sidebars). Word converts px with the paper's factor (0.72pt Letter, 0.70033pt A4; see §3.1). Don't use pt in template markup.
- Put `font-synthesis: none;` on the CV root.
- Design for **one page** with typical content on **both** canvases (850×1100 and 850×1202). Also test a long CV (see §9).
- Arabic: `dir="rtl"` on `<html>`, with `flex-direction: row` (**not** `row-reverse`). No `letter-spacing` and no `text-transform` on Arabic text.
- Phone numbers stay **LTR** inside Arabic CVs (wrap them in an LTR span or use `dir="ltr"`). ✅ This is done for all templates; repeat it in new ones.

### Step 3: Register the template
- Add it to the template registry in `app/registry.py` (block, label, blurb, skill pattern, accent) and to `_PORTED`.
- Add its cover-letter theme (letterhead = **the CV header exactly**, see §10).

### Step 4: PDF check
- Export EN and AR PDFs on **Letter and A4** (4 files). They should already match the preview, because they use the same HTML. Each one is 1 page, on the paper's sheet.
- Run the PDF font check: every face is embedded under its exact name and there is no fallback font.

### Step 5: Word design (the hard part)
- Write the per-template Word design. Use the techniques in **§8** for each visual element from Step 1.
- Use the template's own px sizes, colours (hex) and margins, converted with `docx_design.pt()` / `tw()`. The factor follows the CV's paper (§3.1). Page sizes come from `page_h_px()` / `page_w_pt()` / `page_h_pt()`, never literals.
- Build and open the Word file on **Letter and A4**, in EN and AR.
- Map fonts with the Word weight rules (§7.3), set the Arabic run attributes (§7.4), and call `embed_fonts()`.

### Step 6: Compare (see §11)
- Take before/after screenshots, render the Word file in LibreOffice, compute a **diff %** against the PDF, then do the **Microsoft Word check**. Do all of it on **both papers**.

### Step 7: Tests
- Add the template to the golden tests on **both papers**: `pixels/` and `pixels-a4/`, and the HTML scenarios including `a4`. Golden files are created or updated **only with approval**, and a change to an existing Letter golden needs its own approval.
- Run the fast suite, the e2e suite, `verify_docker_context`, and `test_requirements_cover_imports`.

### Step 8: Save and release
- Use the save orders (§14) and work on a feature branch. **Never push `main`** without approval.

## 5. Lifecycle: EDITING an existing template

1. **Before** screenshots of the website, PDF and Word in EN and AR. Put them in a review folder on the Desktop. ✅ This is a required rule.
2. Change the HTML/CSS **and** the Word design **in the same change**. A change on one side only is a fidelity bug.
3. If you change a font, size or colour, change it in the source of truth (registry or CSS variable). Do not override it inside one output only.
4. **After** screenshots. Show them side by side with the before set.
5. Re-run the comparison (§11) and the tests (§12). Golden files change only with approval.
6. Check the **cover letter** too, because the letterhead copies the CV header.

## 6. Lifecycle: REPLACING or REMOVING a template

- **Replace (same id, new design):** follow §4 Steps 1–7 in full, keeping the id. Saved user CVs that use that id will show the new design. Decide whether that is acceptable before you start.
- **Remove:** don't delete an id that saved CVs may use. Instead hide it from the picker and map old CVs to a close replacement (agree on the mapping first). ✅ Today there is no per-id mapping table: `app/store.py` `load_meta()` sends any unknown or un-ported key to `registry.default_key()`, and taking a key out of `_PORTED` in `app/registry.py` hides it. A specific replacement mapping would be new code. Remove its Word design, letter theme and golden files in the same change.
- **Renumbering ids is not allowed.** Tests, saved CVs and docs all refer to them.

## 7. Typography and fonts (summary of `CVSTAND_FONT_CONTROLS.md`)

### 7.1 Rules ✅
- **One registry** holds all fonts, weights, sizes and defaults. UI, validation, CSS, PDF and Word all read from it.
- **Self-host every font.** Nothing is loaded from `fonts.googleapis.com` at render time.
- **Real weights only** (`font-synthesis: none`). Never offer a weight the font doesn't have.
- The **user's chosen sizes** (typography controls) are stored in **pt**. On the canvas they become px (`× 4/3`, `PT_TO_PX` in `app/typography/render.py`), and Word applies them as `chosen × 4/3 × 0.72` pt (`docx_design.apply_chosen_sizes`). Template sizes themselves are px (§3.1).
- Per-font `optical_scale` and `line_height` (from calibration) are applied when rendering. The user's pt value stays as stored.
- **Step 7 calibration is currently OFF.** ✅ Turning it on changes Jomhuria, Bebas Neue and Lateef (bigger) and Amiri and Scheherazade (smaller). Only turn it on with approval and a full re-comparison.

### 7.2 Default Arabic fonts in PDF ✅
- Name: **Tajawal**. Headings: **Tajawal / Cairo**. Body: **IBM Plex Sans Arabic**.

### 7.3 Word font-name mapping ✅

| Weight | Word run font name | `bold` |
|---|---|---|
| 400 | `Family` | False |
| 700 | `Family` | True |
| other (200, 300, 800, 900) | `Family WeightName` (e.g. `Cairo ExtraLight`) | False |

The name must equal the TTF's **nameID 1** (`word_family_name` in the registry). Read it from the registry; never rebuild it in code.

### 7.4 Arabic runs in Word ✅
Every Arabic run needs:
- `w:rFonts` with **ascii, hAnsi, cs, eastAsia** all set
- `w:bCs` next to `w:b`, and `w:szCs` next to `w:sz`
- `<w:rtl w:val="1"/>` **and** `<w:lang w:bidi="ar-SA"/>` (a paragraph-level `<w:bidi/>` alone is not enough)

### 7.5 Embedding fonts in Word (required) ✅
Every .docx must embed the faces it uses, so it looks right on a PC without those fonts.
- `word/settings.xml`: `<w:embedTrueTypeFonts/>` at the schema-correct position, and **no** `w:saveSubsetFonts`.
- `word/fonts/fontN.odttf`: obfuscated with a new GUID. The key is the GUID's 16 byte pairs **in reverse order**; XOR the first 32 bytes.
- `word/fontTable.xml` entries (`embedRegular` / `embedBold`) plus their rels, and the `odttf` content type.
- Only embed fonts with **fsType 0 or 8**. Respect the OFL **Reserved Font Name** rule (no renamed or modified copies).
- Embed the full script-subset TTF, never only the characters used, so the user can keep editing.

### 7.6 The "Calibri" myth ✅
If Word shows **Calibri** in places, that comes from Microsoft 365 cloud fonts on that PC, not from our code. Check the embedded font list before "fixing" it.

### 7.7 Adding a NEW font
1. Add it to the registry (language, role, offered weights, category).
2. Run `tools/build_fonts.py`. It checks licences, RFN and fsType, builds woff2 + TTF, and regenerates `fonts.css`.
3. Run calibration for `optical_scale` / `line_height`, then look at it on `/dev/typography`.
4. Make sure `.dockerignore` does not exclude the font files (`tools/verify_docker_context.py`). A missing font **does not fail the build**; it silently falls back in production.

## 8. Word techniques: making Word look like the website

These are the techniques that worked in runs 4–14 and the defects / word-pages / word-audit runs (2026-11). Use them for every Modern template; §8.12, §8.18 and §8.20-8.21 apply to ATS templates too.

### 8.1 Page layout
- Word page is the CV's paper: **US Letter 612×792pt or A4 595.3×841.9pt** (§3.1). Positions and margins are the template's px through `pt()` / `tw()` (× 0.72 on Letter, × 0.70033 on A4). Full-bleed elements (bands, sidebars) use **DrawingML shapes anchored to the page**, not table cells, so they reach the paper edge.
- `tblInd` to flush a table to the edge ✅: **-284 twips (LTR)**, **341 twips (RTL)**.

### 8.2 Sidebars and columns
- Draw the sidebar background as a **page-anchored DrawingML rectangle** that runs **from page top to page bottom**. A table-cell shading stops where the text stops (recurring bug #1).
- Put the sidebar text in a table column or text box on top of it.

### 8.3 Page background tint
- If the website page is tinted (light grey, off-white), Word needs a **full-page rectangle behind everything** (or the document background). Missing tint was recurring bug #2.

### 8.4 Header bands
- Draw them as page-anchored rectangles with the exact height from the CSS. Fixed in run 13b for t8, t13, t14 and t17 ✅. Missing band: recurring bug #5.

### 8.5 Timelines
- Draw the vertical **line** as a shape (a line, or a thin rectangle) **as well as** the dots. Missing lines: recurring bug #3.

### 8.6 Pills, chips and rounded boxes
- Use **rounded-rectangle** DrawingML shapes (`roundRect`). A shaded table cell gives a square box (recurring bug #4, t23 pill fixed in 13b ✅).

### 8.7 Photo frames
- Same shape, size and border as the website. Don't add an extra border. An empty photo slot must not show as a coloured block.

### 8.8 Sizes and wrapping
- Sidebar headings and labels in Word must use the CSS px size **× 0.72pt**. Longer Arabic headings (e.g. "المعلومات الشخصية") must not wrap. Check the column width (recurring bug #7).

### 8.9 RTL alignment ✅
- With `w:bidi="1"` on a paragraph, Word mirrors the alignment. RTL paragraphs need **`WD_ALIGN_PARAGRAPH.LEFT`** to appear right-aligned.
- Swap left and right for sidebars, borders and timeline sides in Arabic, matching the PDF (Arabic timeline and border sides were fixed in an earlier run ✅).

### 8.10 Things Word cannot do exactly (agree a fallback)
- Gradients, shadows, blur and CSS-only decorations are approximated with a flat colour or a shape.
- Complex skill sliders are simplified (accepted for التقنية المالية).
- Write the fallback into the template's notes so nobody "fixes" it later.

### 8.11 Bullets and timelines (feature/defects) ✅
- **HTML:** bullets come from `cv_dot()`; timeline dots from `tl_node(x, d, style)` and line pieces from `tl_seg(...)` (`app/rendering.py`). Never hand-draw a dot or rail in a template.
- **Word:** the shared `Timeline` helper (`word_designs/common.py`). It places each node level with its entry's FIRST title line, counting the title's space-before. It masks the line above the first node and draws the last entry's stretch only down to its node.
- **The line starts at the first dot and stops at the last dot**, in HTML, PDF and Word. It never runs past the last entry.
- **The rail's x is the PDF's.** A rail drawn as a cell's end border sits at that cell's edge. If the node cell is wider than the PDF's offset, the rail moves *and* the text column shrinks. modern-t20 used a 27px node cell, which put the rail 25px in and took 25px off the text; 3px is right (feature/word-audit).

### 8.12 Rules, leaders and thin lines ✅
- **Heading rules and leaders are drawn in Arial** (`rule_heading`, docx_ats `_rule_tab`). A leader in the body font's underscore draws dashed in many faces (t2 t12 t22 Arabic, ats-t15).
- **A CSS rule element needs `flex-shrink:0`** in a flex column. Without it the 1–3px rule collapses to 0px on the site and in the PDF (ats-t3 t6 t10 t13 t14, feature/defects).
- **ATS Word (docx_ats):**
  - A div rule **keeps the gap above it**. `tiny()` resets spacing, so always pass `before_px`; ats-t10/t14 rules sat on the line above until feature/word-audit.
  - A div rule **keeps its own CSS width**: ats-t14's 74px accent was drawn full width.
  - A box drawn only by its borders (ats-t9's 3px + 1px double rule) must still write a paragraph; it used to write nothing.
  - **A left/right paragraph border runs through the space between paragraphs, whatever the group.** Two sections with `border-inline-start` 14px apart drew ONE unbroken bar (ats-t18). The gap goes into an empty unbordered paragraph (`_split_side_rules`).
- **Word clips the top of a line set under single spacing** (multiple < 1.0). modern-t12's Anton name lost its top 10px at 0.9. Use ≥ 1.0 and take the space back elsewhere.

### 8.13 Exact heights: the narrow exception ✅
- Word line spacing is **Auto**, never Exactly, with one exception (user decision 2026-11-20): **an exact row height only on a single-line decorative band** (one text paragraph whose before + 1.51em fits), and an exact line only on a paragraph with no text.
- `tests/test_docx_flow.py::test_no_exact_spacing_anywhere` enforces it. Don't widen it without the owner's approval.

### 8.14 Rounded corners and masks ✅
- `round_corners()` puts four small in-front masks on a filled block. **Each mask is the colour BEHIND the block, i.e. the page colour** (`WORD_PAGE`, or the band/column under it), never the block's own colour.
- Masks overlap the block's edge by `CORNER_OVERLAP_PT`. A mask edge exactly on the cell edge left an anti-aliased hairline in Word's PDF (t5/t21 pills).
- A header card with rounded **bottom** corners needs its bottom masks on the card's last paragraph, not the paragraph after the table (t21: stray lime wedges at the card's foot).
- A rounded card that must reach the page foot (modern-t21's side card) is a **page-anchored `roundRect`** (VML + DrawingML) from its top to the page foot minus its margin, placed in the header and copied into the body (`body_page_shapes`). It is not a cell.

### 8.15 Full height on EVERY page, CV AND letter ✅
- Sidebars, columns, bands and column **rules** that the PDF carries to the page foot must reach it in Word **on every page, in the CV and in the cover letter**.
- A cell shading or cell border **stops where the cell's text stops**. In the letter the CV content is emptied, so a cell-drawn column shrank to ~1/3 of the page (modern-t21 letter, feature/word-audit).
- Use page-anchored shapes: `page_rects`, the t21 side card, and `SidebarPage.rule_to_foot(x, colour, foot_px)` for a divider. Keep the cell border for the divider's exact top; the shape continues it to the foot (modern-t1, t6).
- Put the shape at the **PDF's x**. modern-t1's side column was 30px wider than the PDF's, so the divider sat 30px off and the main column was 30px narrower. Measure the PDF's boxes in Chromium (`getBoundingClientRect`, border-box) and copy them.
- **Never let a header part exist by accident.** Reading `section.header._element` CREATES a header with Word's default ~14pt paragraph, and every page then starts that far down. modern-t13's band sat 17–21px below the paper's top. `body_page_shapes` and `finish_rtl` check `is_linked_to_previous` first. Shapes added after `flat_headers()` (in `after_lines`) must `tiny()` their header paragraph.

### 8.16 The photo frame is identical in CV, letter and PDF ✅
- Same size, shape, crop and position as the PDF, and **the same in the CV and the cover letter**.
- A photo that **shrinks with its column** (flex-shrink, modern-t20) is a different size on every CV:
  - **HTML:** mark it `class="cv-photo"`. `app/letter.py` keeps its column hidden in place, so the PDF letter's photo is the CV's size; it used to be full size in the letter.
  - **Word:** the letter copies the CV's frame (`docx_letter._photo_like_cv`). `shrink_side_photo`'s reserve is measured per template in real Word.
- A photo partly covered by another box (modern-t14's orange panel) is a documented simplification. Write it in the design's docstring.

### 8.17 The cover letter (Word) matches the PDF letter ✅
- The PDF letter hides CV content in place in the band and in the name's column (`keep_place`). The Word letter does the same with `_blank`.
- `_blank` must keep the **name and headline** even when the summary repeats them. The Arabic demo summary starts with the title, and t14/t17 lost their headline.
- A blanked table loses its borders too. modern-t8's pale chip rule stayed in the letter.
- When the PDF letter puts the body somewhere other than the CV's job column, or drops a heading row or a rule, the design says so with `ctx.doc.cvstand_letter = {"cell", "width", "drop", "unrule"}`. modern-t12 uses it to place the body beside the contact list and drop the heading row; t13 uses it to drop the band rule over the hidden chips.
- **PDF side (`app/letter.py`):** an emptied page-level section box drawn only by its border is removed below the body. ats-t5 printed two grey lines under the signature.

### 8.18 One page in real Word: per-template reserves ✅
- The Word page estimate (`docx_measure`) is **not exact**:
  - English text in real Word runs taller than the estimate (Word's line metrics, mixed metric faces, keep-together rows, labels that cannot break). Arabic can run long *or* short.
  - So templates carry **measured** reserves: ATS `EN_RESERVE_PT`, `EN_TYPE_FIT_KEYS` and `AR_RESERVE_DELTA_PT` in `docx_ats.py`; Modern `page.main_reserve_pt`, `fit_side(reserve_pt=...)` and `ctx.side_bias_pt`.
  - Each value is commented with the sweep that chose it.
- **Measure in real Word, never guess.** Sweep the value over a few steps on the demo AND sample CV, Letter AND A4 (the sample CV on Letter is the hardest page), and take one step past the first value where all four are 1 page.
  - Tools: the scratch sweep pattern (render each value to docx, convert with `tools/word_com.ps1`, read the page count) or `tools/word_audit.py`.
- What doesn't move the result:
  - **Find which column really spills before choosing the knob.** In a `SidebarPage` the side cell is merged down the main column's rows. When the main column's last row breaks to page 2, the side column's last blocks go with it, so a spill that *looks* like a side spill is a MAIN spill: use `main_reserve_pt` (modern-t5/t9 English).
  - A side bias that forces the type ladder shrinks EVERY CV of the template, the demo included, and leaves an empty column foot. Don't use one for this; it was tried and reverted in feature/word-audit.
  - A larger **fit_side** reserve only gives up gaps.
  - An English ATS page that is still over at gaps 0.85 needs the type steps (`EN_TYPE_FIT_KEYS`).
  - A reserve that pushes the estimate past `TYPE_FIT_PAGE_MAX_PT` switches the fit OFF.

### 8.19 The RTL PDF shift ✅
- Chromium printed every RTL document 850×(1−scale)px too far LEFT (34px Letter, 57px A4), and every A4 document 1px right. `app/exporters/pdf.py PRINT_ORIGIN` pins the canvas to the page origin.
- `tests/e2e/test_pdf_bounds.py` and `tools/pdf_bounds.py` check that all 392 PDFs (49 × EN/AR × Letter/A4 × CV/letter) stay on the page. The test takes ~630s, so split it with `-k`.

### 8.20 Proving a Word change touches only what it should (docx hash) ✅
- Hash every Word export before and after (demo + sample + photo CV × EN/AR × Letter/A4 × cv/letter/both). Mask `docProps/`, `word/fonts/*` and `fontTable.xml`, because the obfuscation key is random.
- **Reset `docx_dml._ID[0] = 0` and `docx_design._SHAPE_N[0] = 0` before EVERY render, in BOTH runs.** These are process-wide id counters: one extra ladder build shifts every later file's ids (416 false differences the first time).
- The baseline comes from a clean `git worktree` of the previous commit.
- Do the same for the PDF side: hash `document_html` and `letter.document_html` for every template.

### 8.21 The real-Word audit (`tools/word_audit.py`) ✅
- Stages:
  - `gen`: docx with the counters reset, plus the PDF of the same CV via `_print`.
  - `word`: real Word through `tools/word_com.ps1`, our own WINWORD PID only.
  - `raster`: `tools/pdf_raster.ps1`, Windows.Data.Pdf, 850px wide.
  - `check`: `failures.csv`.
  - `sheets`: contact sheets PDF | Word per template.
- Run it as `python tools/word_audit.py all <work> [--keys k1,k2] [--src demo,sample,photo] [--ref <earlier work>]`. `--ref` reuses an earlier run's PDFs after a Word-only fix.
- Checks per page:
  - page count (cv 1, letter 1, both 2);
  - columns/bands start and end where the PDF's do (fill map, ±14px);
  - stray / missing lines and dashed rows;
  - text cut off or moved to another page (Latin tokens; Arabic letter counts);
  - text off the page;
  - photo frame vs PDF, and CV vs letter;
  - letterhead = CV header.
- Word export needs **full normalised paths** (`[IO.Path]::GetFullPath`). With a raw joined path, `ExportAsFixedFormat` hung on every file until the job timed out.
- Never run two Word jobs at once, and never while the browser suite runs.
- Known instrument limits:
  - Windows.Data.Pdf does not draw the PDF's conic-gradient patterns (skill rings in t12/t24), so those show as missing in the PDF image.
  - Word's line positions shift with text reflow, so a rule's y is compared within ±120px. Check a flagged rule by eye on the contact sheet before fixing it.

## 11. Fidelity verification workflow (required for every visual change)

1. **Before/after screenshots** of the website, PDF and Word (page 1), EN + AR, on **US Letter AND A4**, in a Desktop review folder.
2. **Automated compare:** render the .docx with LibreOffice to PNG, compare it with the PDF page 1, and record a **diff %** per template.
   - Rough guide from the AR review: under ~10% = close; 10–20% = check; over 20% = something big is missing (band, tint, overflow). These are rules of thumb, not formal thresholds.
3. **Microsoft Word check (required):** LibreOffice findings are hints only. Confirm each issue in **Microsoft Word** before fixing it.
3b. **The full real-Word audit, BEFORE a new or replaced template is approved** (§8.21):
   - `python tools/word_audit.py all <work> --keys <id>` covers both papers, both languages, cv / letter / both, and the demo + sample (+ photo) CV.
   - `failures.csv` must be empty, or every remaining row explained.
   - Look at the contact sheets (`sheets <work> Desktop\review-word-audit-<date>\`).
   - Then prove the scope with the docx + HTML hash (§8.20).
3c. **The download lock (§17):** `pytest tests/test_download_lock.py` must list ONLY the templates the task names. After the owner approves their new look (`tools/lock_downloads.py sheets --keys <id>`), run `tools/lock_downloads.py update <id> --approved "..."`. A brand-new template is locked with `update` too, after its approval.
4. **Font-embedding check (before calling fonts "done"):** open the .docx on a **Windows PC where the fonts are NOT installed**. There must be no repair prompt, the fonts must be correct, and typing must keep the font. Record the Word version. A test on the developer PC proves nothing.
5. **Checklist per template** (tick every row in EN and AR):

| Check | ✔ |
|---|---|
| One page on **Letter AND A4**: preview, PDF and Word (EN + AR) | |
| Nothing ends at 1100 on A4: full-height rails and sidebars reach 1202px / the sheet's bottom edge | |
| Same layout and column widths | |
| Sidebar / columns / bands / column rules reach the page bottom on EVERY page, **CV AND cover letter** (§8.15) | |
| Page tint present | |
| Header band present, correct height, starting at the paper's top edge (no stray header part) | |
| Timeline line + dots: dots from `cv_dot()` / `tl_node`, the line from the first dot to the last, rail at the PDF's x (§8.11) | |
| Pills rounded; corner masks in the page colour; no wedge at a card's foot (§8.14) | |
| No stray lines, dashes or borders; rules and leaders in Arial; rules keep their gap and width (§8.12) | |
| Exact row heights only on single-line decorative bands (§8.13) | |
| Same fonts (names) and sizes (Word pt = CSS px × 0.72 on Letter, × 0.70033 on A4) | |
| No heading wraps that the website doesn't have | |
| Same page count: cv 1, letter 1, both 2, demo AND sample CV, measured in real Word (§8.18) | |
| PDF stays on the page, RTL included (`test_pdf_bounds`, §8.19) | |
| Phone numbers LTR in Arabic | |
| Photo frame matches the PDF and is identical in the CV and the letter (§8.16) | |
| Cover letter header = CV header; the letter body where the PDF letter has it (§8.17) | |

## 17. Download lock: approved downloads can never change silently

**Approved downloads are locked. A change may only touch templates the task names. Run the download-lock test before every commit. Never update the lock without the owner's approval.**

What is locked: every download a user can make, which is the word audit's matrix. That is 49 templates × demo / sample
(/ photo for the 16 photo templates) CV × EN / AR × Letter / A4 × cv / letter / both = **1368 downloads, PDF and
Word**. The lock is the **current approved state**, known issues included (`docs/KNOWN_TEMPLATE_ISSUES.md`).

| Tier | What it compares | Where the lock lives | When | Time |
|---|---|---|---|---|
| 1 fingerprints | PDF: sha256 of exactly what Chromium prints (CV HTML, letter HTML at no fit and at a fixed fit, paper, faces; fonts, CSS and autofit.js are inlined). Word: sha256 of every .docx part, with `docx_dml._ID` / `docx_design._SHAPE_N` reset per file (§8.20), docProps masked, fonts de-obfuscated (the random key is masked, a changed font is not) | `tests/golden/downloads/<template>.json` (git) | **every commit** | ~3.5 min (8 processes) |
| 2 page images | every page at 100 DPI: the Chromium PDF, and REAL Word (own process only), with the pixel gate's tolerance (8/255, 50 px) | PNGs in `~/cvstand-download-lock/` (outside git, ~190 MB; `CVSTAND_LOCK_DIR`), their hashes in the template's json | **before merges** | ~45 min |

The printer (Chromium, Playwright) and Word versions are in `_printer.json` / `LOCK.md`. A new Chromium is a tier-2
event: run the images before trusting tier 1.

**On a failure:** the test names every moved download (`template · cv · language · paper · part · PDF|Word`, plus the
changed .docx parts). It writes `before | after | diff` images to `tests/e2e/artifacts/download-lock/` (Word through
real Word, own process, first 40 files). Then:
- the template is **not** named by the task → the change is wrong: scope it;
- the template **is** named → show the owner (`tools/lock_downloads.py sheets --keys <id>`, Desktop folder), and
  after their approval:
  `python tools/lock_downloads.py update <id>[,<id>...] --approved "<who approved what, when>"`.
  - It refuses no names, `all`, wildcards, more than 5 templates and a missing approval note.
  - It rewrites only the named templates' json, images and `LOCK.md` rows, and asserts that every other lock file is
    byte-identical.

**Images lost?** `python tools/lock_downloads.py rebuild-images` restores the store from the commit that last changed
each template's json (a scratch git worktree), and reports how many page sets match the locked hashes.

**Contact sheets for approval:** `python tools/lock_downloads.py sheets [OUT] [--keys ...]`. It makes one PNG per
template: rows = CV / language / paper, columns = preview | PDF | Word for the CV, the letter and CV + letter
(default `Desktop\review-download-lock-<date>\`).
